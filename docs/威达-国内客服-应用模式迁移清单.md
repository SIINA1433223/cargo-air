### 关于接口（2026-10-13 核实过，推翻我之前的说法）

我原先写「应用模式只能在网页里点、API 帮不上」——**这句话不准确**。飞书有多维表格应用模式的开放接口，
lark-cli 的 `+app-create` / `+app-page-*` / `+app-block-*` 就是它的封装，底层 REST 路径已核实为：

```
/open-apis/base/v3/base_apps                          # 创建应用（需要 workspace_token）
/open-apis/base/v3/base_apps/:app_token/pages         # 页面
/open-apis/base/v3/base_apps/:app_token/pages/:page_id/blocks   # 页面组件
/open-apis/base/v3/workspaces/:workspace_token/entities
```

**但这条路对当前这套配置走不通**，三条硬理由（都用只读探针验过，
`backend/scripts/probe_app_mode_api.py`）：

1. **这个 base 还没有应用模式，也没有 Workspace**。`GET base/v3/base_apps/{base_token}`
   回 `800008200 底层 GetBaseApp 调用失败`；`GET base/v3/bases/{base_token}` 回的
   `workspace_token` 是**空字符串**。而 `+app-create` 的 `--workspace-token` 是**必填**——
   没有 Workspace 就创建不了应用，没有应用就没有 page_id，组件就无处可加。
   （注意：`800008200` 也可能夹着「我们这组凭证看不到」，两种解释都指向同一个结论：从这里发起不了。）
2. **需要的是一套新的 scope**：创建要 `base:appmode:create` + `base:workspace:update`，
   建页面要 `base:appmode_page:create`。我们后端应用一直用的是 `bitable:app` 那套。
   加 scope 并重新发布，是**你在飞书开放平台上对我们应用的操作**，我不该擅自扩权。
3. **接口面向的是「用户身份」**（CLI 里 `+app-*` 的 AuthTypes 是 `user`/`bot`，官方推荐 `--as user`）。
   后端手上只有应用凭证。

所以分工没变，但理由要更正：不是「没有接口」，是**接口的入口（Workspace + 应用本身 + scope）得先有你**。
你把「应用」建出来的那一下之后，剩下的字段配置我是有机会接手用接口做的。
| 表所在 | 威达 base `Ane6bNFAYacsUPsi3gscwy7hnPb`，商机主表 `tblXmBgagFcTGWJr`（现有 75 行） |
| 权限模型 | 应用权限（页面/数据/功能 + 自定义角色）**独立于**源表；但**行级范围来自「高级权限」**——应用模式里视图的筛选权限只有开/关 |

## 3. 权限配置（搬过去最大的收益，但有个坑要先决定）

**目标效果**：客服在新应用里只看到商机负责人是自己的商机——和现在一样。

> 只有**国内客服**需要配这一段。航线价格 / 国内操作两个工作台今天在代码里就**没有**行级权限
> （全量可见），搬过去保持不动即可——见附录 A.3。

有两条路，**建议先走 A**：

### 方案 A. 用视图筛选（推荐，零风险）
1. 在商机主表建一个视图，例如「我的商机」，筛选条件：`商机负责人 等于 [当前用户]`。
   - 待验证：飞书视图筛选的人员字段能不能选「当前用户」。能，则这条路成立。
2. 应用模式的列表组件**挂这个视图**当数据源。
3. 高级权限**一个字都不改** —— 客服在飞书表格里的所见和今天完全一样，不会因为上新系统而改变工作习惯。

### 方案 B. 用高级权限的记录规则（真正的权限，但会改动现状）
1. 高级权限 → 角色「国内客服」（已存在）→ 数据权限 → 商机主表 → 记录权限
2. 可编辑和删除的记录范围 →「与成员本人相关的记录」→「以下字段包含成员本人的记录」→ `商机负责人`
   - 这条官方明确**只支持人员字段**，而 `商机负责人` 正是人员字段，所以能配
3. ⚠️ **副作用**：这会让「国内客服」这 3 位（Lee Li、Gary Yuan、Henry Cao）**在飞书里直接打开商机主表时也只能看到自己的行**。这是对现有工作方式的实质改变——先跟这三位确认他们现在是否需要看全表，再决定。

### 其他两条（无论走 A 还是 B）
- **应用权限**（页面权限 / 数据权限 / 其他功能权限）独立于源表：列表组件里的按钮是否可操作、能否复制应用内容，都在「应用权限」里按角色配。应用内的自定义角色可以照现有 4 个部门角色一一对应。

### A.3 ✅ 只有国内客服有行级权限，另两个部门没有

这是个**简化**，不是问题。代码里只有国内客服的工作台配了 `owner_field="商机负责人"`
（`workbench.py:1084`）；航线价格和国内操作**都没配**——也就是说这两个工作台今天在自建系统里
**本来就是全量可见**（航线价格 122 行、国内操作 32 行，谁打开都一样）。

所以搬过去时：
- **航线价格 / 国内操作：行级权限一个字都不用配**，高级权限和现在一样不动，行为就一致了。
- 国内客服：才是需要按 §3 走 A 或 B 的那一个。

顺带探到一件事，记下来免得以后绕弯：订单表的 `国内操作` 是**单选**（不是人员字段），
`操作负责人`/`商机负责人`/`负责航线` 全是**查找引用**——**订单表上没有任何一个字段能当
行级权限字段用**。也就是说，国内操作这一岗**今天就算想收窄也做不到**（除非改字段类型）。
这不是本次要解决的事，但以后如果业务提出「操作的同事只想看到自己的单」，答案在这里。

### A.4 三个部门共用的事项

  `check_page_spec.py all` 逐项比对，确认搬过去没漏字段。

## 7. 会丢掉什么（2026-10-13 代码审计后补，**这份清单不是零损失**）

> 前面 §0-§6 只讲「字段和页面怎么摆」。那是**不够的**。下面是逐文件读出来的、字段显示之外
> 由代码实现的行为，按「纯界面配置能否还原」分类。

### 7.1 ✅ 应用模式原生就更好（现在这些代码只是在补飞书 API 的短板）

| 能力 | 现在为什么要代码 | 应用模式 |
|---|---|---|
| 按钮字段（确认订单等 4 个） | 接口**点不动** 3001，只能去飞书里点 | 原生能点 |
| 附件下载 / 预览 | 要后端代理 + `extra.bitablePerm` + 传对 `tableId`，否则 400/403 | 原生 |
| 「操作」阶段条（type 24） | 读不出节点，只能问人 | 原生渲染 |
| 新建商机表单 | 自己读 `/forms/{id}/fields` 再渲染一遍 | 原生表单 |
| 导出 | 现在**没有**导出功能 | 飞书自带 |
| 字段值形态适配（公式 `type/value`、关联裸 dict、日期线索…） | 一堆 `normalize_field_value` 兜底 | 不存在这个问题 |
| 多级 Redis 缓存（字段/状态/表单/通讯录 30s~1800s） | 为了把 20.85s 压到 0.97s | 不存在这个问题 |
| 行级权限 | 拿 `sys_user.name` 去通讯录**精确匹配**换 open_id，差一个字直接报错 | 原生「商机负责人 = 当前用户」 |

### 7.2 ⚠️ 要靠飞书自动化/公式重做，**能不能等价还原未验证**

| 能力 | 出处 | 风险 |
|---|---|---|
| **单票状态**（六档判定链，客服催办的核心） | `service.py:733-766`、`:2158-2187` | 要跨商机+订单两表，且含「未拿到货**且有备注**才算完成」这类边角；公式/自动化拼得出来但要逐条验 |
| 待办分项计数卡片 | `service.py:2950-2973` | 每个勾选框独立计数 → 要多个仪表盘块 |
| 就地编辑的失败回滚 / 描边状态 | `WeidaWorkbench.vue:963-989` | 飞书明细表能点格即改，但没有这套反馈；属体验降级不是功能缺失 |

### 7.3 🔴 应用模式**没有对应物**，迁移就是丢

| 能力 | 出处 | 影响 |
|---|---|---|
| **合并组 + 联动同步** | `service.py:2750-2844`（并查集重组）、`merge-group.ts` | 多票合单报关/订舱；改订舱信息**整组一起改**；跨组重组、拆分不残留。飞书没有「合并组」概念，靠「组号」+自动化只能覆盖一部分 |
| **个人化的列 / 筛选 / 布局** | `WeidaColumnConfig.vue`、`view-config.ts`（存 localStorage `weida_view_config:{userId}:{role}`） | 每个客服自己配列、拖列宽行高列序、整格整行整列**填色**、把筛选存成「我的待报价」。飞书视图是**共享**的，且不支持拼接列/填色/拖行高 |
| **拼接列 + 「空列」** | `view-config.ts:120-140,318-326` | 拼接列（`{字段名}` 占位拼文本）飞书没有；「空列」是**真去飞书表新建字段**，也不该由界面做 |
| **「分单号逐条改」面板** | `WeidaWorkbench.vue:1180-1260` | 把一个**只读查找格**变成「逐条改 iFreight 记录」的编辑器。应用模式做不到（**这条属国内操作**） |
| 对客方案费用明细对话框 | `WeidaCostDetailDialog.vue` | 把飞书按钮换成自建 CRUD 表格 + 43 个费用类别动态成列 |

### 7.4 结论

**要迁移的不是「字段」，是「跨表派生状态 + 合并组算法 + 个人化视图 + 把只读列改造成可写编辑器」这一整套。**
纯界面配置（本文 §0-§6 的做法）**能搭出一个"能看数据、能改字段"的壳，但会丢掉 7.3 里的全部能力**，
其中「合并组」和「个人化的列/筛选/填色」是客服**每天在用**的。

这也意味着：**7.3 里的东西如果业务不能放弃，那"只做应用模式配置"这个方案本身就不成立**，
需要重新决定是补自动化、还是保留自建系统、还是分岗迁移。
